# Composition and Migration

technical-report-writing is the authoring entry point for documents in any medium. It owns content selection, information design, noun-phrase headings, compact tables, focused figures, explanation, language, and production. share-internal-doc adds colleague suitability, usable source access, and authorized delivery. Naming share-internal-doc alone remains sufficient for a complete shared-document request: it applies the available writer rather than making the user invoke another skill.

Use the writer's source and production references without maintaining copies here. When revising an existing project, preserve its source of truth, useful figures, and medium choices. A document may be directly maintained Markdown, a native editable document, or generated output; do not impose Markdown as universal source.

insight-dashboard owns analytical comparison and selection-consistent views. The terminology pair owns accepted project expressions and their sources. Use only the specialist capabilities needed for the requested result. The writer and specialist tools come from other packages; if unavailable, preserve the established preferences and perform the request with available tools. Do not silently install another package.

Keep the writer's explicit editorial defaults in force through preparation and delivery. Genre determines the necessary explanation: a concise factual report is not the template for a technical introduction or proposal. A sharing review should catch lost context, inaccessible citations, and conversion damage; it should not duplicate the writer's whole procedure or automatically run another polishing pass.

The earlier reader-and-structure, claims-and-sources, editorial-examples, reader-review, and medium-and-figures references duplicated writing responsibilities. General methods now live in the writer. The sharing pass remains here. Old project artifacts and uncommitted work are not removed by this package migration.
