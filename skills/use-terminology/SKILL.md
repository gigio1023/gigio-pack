# Use Terminology

Use the project's accepted terms and expressions while completing the requested task. Give the reader an accurate explanation or a corrected artifact, not an unnecessary glossary report. Established English terms come first; explain their meaning in the reader's language without literal translation that changes the field's meaning.

## Read the relevant reference

Read the project's instructions and terminology entry point at task start when required, then the relevant topic, internal-name, and anti-pattern entries. Resolve those links from the document's location. Search within that material before widening to the project's source index; do not load the entire literature collection or a historical glossary merely because it is longer.

Apply entries to their documented domain, version, conditions, and level of claim. Keep an internal identifier distinct from a reader-facing name, a source-specific metric distinct from a general concept, and an editorial restriction distinct from a claim about all industry usage. Explicit project wording decisions take precedence over a generic preference to retain a familiar term; preserve the protected quotations and identifiers specified by that decision.

When the user asks about a term, return the accepted English expression, its contextual meaning, the distinction that resolves the question, and a useful source pointer. Do not turn an ordinary phrase into a named method. When drafting, use the terms naturally and retain the qualifiers that determine their meaning. Consult [application pitfalls](references/application-pitfalls.md) when a familiar label hides a different operation or a stronger claim.

## Correct what the task authorizes

In a writing or editing task, fix confirmed terminology and expression problems in the directly managed artifact before finishing. An explicit standing project instruction may also require correcting documents encountered during other tasks; perform that work in the same task without waiting for another correction request. Respect an explicit read-only or review-only restriction: return the exact problem and proposed correction without modifying files.

A lookup request by itself grants no file edits. Quotes, collected originals, archived records, APIs, schemas, and identifiers retain their original form; correct the explanation around them. External edits and publication use the existing authorization for that service. If the original cannot be changed, describe the correction and, when local recording is authorized, put it in the project's correction record.

If the accepted reference is wrong, stale, contradictory, or missing the needed concept, do not pretend it settles the answer. Identify the narrow gap and inspect the available primary source needed for the immediate task. Use a qualified plain-language description while uncertainty remains. Route a requested or standing-authorized definition update to `curate-terminology`; do not start broad research, paper downloads, or a parallel glossary from a lookup-only request.

## Return to the work

Check the final answer or edited passages for stable names, preserved qualifiers, source fit, and compliance with project-specific expressions. Verify links and the project's required document checks for files changed. State material corrections and unresolved meaning briefly, then continue the original task. `curate-terminology` owns reusable definition and expression records; this skill owns applying them.
